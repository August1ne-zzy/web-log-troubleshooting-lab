# 障害記録 001：模擬依存先の設定誤り

## 実験の範囲

ローカルの合成 GET リクエストのみを使用します。依存先は JSON のブール値で模擬し、外部サービスへの接続や実ユーザーへの影響はありません。実装・実行・記録は AI 支援によるものです。作者による未知の本番障害の独立診断を示す記録ではありません。

## 再現と観測

```powershell
python incident_demo.py
```

毎段階で `/` と `/report` を各 1 回要求します。新しいループバックサービスと独立した設定ファイルを使用するため、通常の設定を変更しません。

| 段階 | dependency_ready | `/` | `/report` | 5xx / 総件数 | 5xx 率 |
| --- | --- | ---: | ---: | --- | ---: |
| baseline | true | 200 | 200 | 0 / 2 | 0% |
| fault | false | 200 | 500 | 1 / 2 | 50% |
| recovered | true | 200 | 200 | 0 / 2 | 0% |

上記の状態と件数は保存済みの [実験ログ](../examples/incident/access.jsonl) と、段階別の SQL 集計結果（[正常](../examples/incident/baseline.md)・[障害](../examples/incident/fault.md)・[復旧](../examples/incident/recovered.md)）で確認できます。

## 調査の流れ

1. **発見**：fault 段階の SQL 集計で 5xx を 1 件確認。
2. **範囲の特定**：パス別集計では `/report` のみ 5xx、`/` は 200。サービス全体の停止とは異なる。
3. **原因の確認**：`/report` の処理を読み、設定 `dependency_ready` が応答を決めることを確認。実験で false に変更した設定が原因。
4. **修正**：設定を true に戻す。サービスはリクエストごとに設定を読み直すため、再起動不要。
5. **復旧確認**：同じパスを再要求し、`/report` が 200、5xx が 0 / 2 になったことを確認。

自動デモは原因をあらかじめ設定しているため、観測から独立に原因を発見した実績とは区別します。次の本人演習では、ログ → パス別 SQL → 処理コード → 設定の順に確認します。

## 復旧判定の注意

段階別に異なる DB に保存し、それぞれ 2 件を分母にします。履歴をすべて混ぜると過去の 500 が残るため、「復旧後もエラーあり」と誤解する可能性があります。実運用では時刻やデプロイなどで観測対象を区切る必要があります。

`/error` は常時 500 の確認用パスであり、この修正の対象外です。2 件の成功だけで長期的な信頼性や性能改善を主張しません。今回確認できるのは、設計した設定変更と応答の関係、および同じ要求での復旧です。

## 改善候補

設定不正と模擬依存先未準備を識別するログ、起動時の設定検証、より多い検証リクエストを検討します。現在はこれらを実装済みとは扱いません。
